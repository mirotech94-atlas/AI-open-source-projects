## How they open

The official n8n course episode starts as part seven of a series and goes
straight to where past runs are stored, with no hook. The Nate Herk video
states its promise in the first ten seconds (one error workflow, linked to
every active workflow, logs and alerts) and then shows the test workflow it
will break on purpose. The Michele Torti video gives a short credentials
intro, then names the first technique and opens a node within half a minute.
None shows the finished result first; the closest is naming the outcome.

## The order they explain things

- n8n course: where executions live (production vs manual runs, the
  execution log, a past run as a read-only snapshot), then why runs fail,
  then the error workflow, then Stop and Error, then a build in the editor.
- Nate Herk: activate the workflow first (an error workflow only fires for
  active ones), build the logger with the Error Trigger, link it in the
  workflow's settings, break the workflow on purpose, read the captured run,
  then map the fields into a sheet and a Slack message.
- Michele Torti: five techniques from lightest to heaviest: retry on fail,
  continue on fail, a split error output, a fallback chat model inside the
  AI Agent, then the error workflow.

## Examples and analogies

- A daily sheet-to-CRM sync where some rows have no email, so the CRM node
  fails on those items (n8n course).
- A webhook whose email field is checked, raising Stop and Error when it is
  not valid (n8n course).
- A random dog-picture API, broken by deleting one letter of the URL, to
  show retries and the error branch (Torti).
- An assistant agent made to fail by unplugging its chat model (Herk).
- The language model described as the agent's brain (Torti).

## Beginner mistakes they address

- Expecting the error workflow to fire for a workflow that is not active.
- Not knowing manual test runs are not kept in the log by default.
- Forgetting to set the error workflow in each workflow's settings.
- Using continue-on-fail on a step the rest of the flow depends on: the run
  looks green while the data is an error message.
- Treating a provider outage as a bug instead of retrying after a pause.

## Pacing

Measured above: from about 127 to 260 words a minute. The course episode
is slow, with slide-like explanation before the editor; the two creator
videos talk fast and stay in the editor. All three keep one workflow on
screen and change one setting at a time. Chapters are named by what happens
in two of them; the third numbers its chapters "Method 1" to "Method 5",
which tells a searcher nothing.

## What they do badly, and what we do better

- No video opens on the finished alert or log. We open on the Slack alert
  and the failed run it points to (the result-first opening).
- Generic chapter names (Method N). Ours name the node or setting.
- One pushes a community sign-up for a template. Our lab file is a free
  download from the store, no sign-up.
- Retry intervals and counts are shown without saying why those numbers.
  We say the default and that it is a choice, never a recommendation we
  cannot back.
- Fast speech over dense screens; we keep our pace and hold each value.

## What we take (structure only)

1. Show a failing run first and read it in the execution view.
2. Order the fixes from the node level (retry, continue, error output) to
   the workflow level (an error workflow with the Error Trigger).
3. Break the workflow on purpose, on camera, to prove the error path works.
4. End on the alert that names the workflow, the failed node and a link to
   the run, as the check that it worked.
5. Name the one gotcha that makes it silently not work: the workflow must
   be published/active and linked in its settings.
