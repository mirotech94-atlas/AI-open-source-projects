## How they open

None of the three opens on a result. Oskar has no hook at all: one sentence
names the two kinds of webhook URL (test and production) and the editor is
on screen by the half-minute mark. Ben Young recaps the previous episode of
his series, then spends about a minute on his own career before the topic,
and states the question (what if n8n has no node for this app?) only in
passing. Nate Herk promises to explain APIs so simply anyone gets it, then
gives roughly eight minutes of theory slides before n8n opens (first action
at 487 s, the slowest start we have measured on this topic).

## The order they explain things

- Oskar: the two webhook URLs, call the test URL from a browser, add query
  parameters, branch on one with an IF node, switch the response mode to a
  Respond to Webhook node and redirect, return a generated HTML page, and
  last a scheduled workflow calling another workflow's webhook through an
  HTTP Request node.
- Ben Young: take an existing weather workflow, unplug its built-in
  weather node, add an HTTP Request node, read the provider's docs, try the
  URL in a browser first, move the query string into Send Query Parameters,
  then map the city from the webhook so the call is dynamic.
- Nate Herk: what an API is, why it matters, everyday examples, the five
  methods, REST and endpoints, then three requests in n8n (a weather GET,
  a fake-data GET on two endpoints, a search POST with a JSON body), and
  finally the built-in nodes as the same requests with forms on top.

## Examples and analogies

- A link with brand and action parameters that redirects a subscriber or
  shows a coloured confirmation page (Oskar).
- A city weather lookup, first with the built-in node and then rebuilt
  with the generic request node to prove they give the same answer (Young,
  and Herk with fixed coordinates).
- A free placeholder API used to show that changing the path changes the
  resource you get back, posts versus comments (Herk).
- A news search API called with POST, the topic and result count in the
  body (Herk).
- The API pictured as a restaurant waiter carrying the order between you
  and the kitchen; the methods pictured as reading a book, posting a
  letter, swapping or editing pages, and tearing one out (Herk).

## Beginner mistakes they address

- Calling the production URL while the workflow is not live, or the test
  URL while the editor is not listening (Oskar, Young).
- Hard-coding a value in the URL instead of mapping it from the trigger,
  so every call asks about the same city (Young).
- Sending a call with no query, so the next step has nothing to read; the
  run hangs and the fix is to add the parameter (Young).
- A node left disconnected or disabled after a swap, which makes the run
  look fine up to the gap (Young).
- Parameter names that do not match the docs, or a stray space in a key;
  the cure both give is to reread the provider's documentation.

## Pacing

Measured above: from about 155 to 219 words a minute. Oskar is short and
even, one change per sentence, under six minutes. Young is moderate but

made live. Herk is the fastest and the most front-loaded: half the runtime

## What they do badly, and what we do better

- No one shows the finished round trip first. We open on a browser link
  with a city in it and the answer coming back.
- Two of them paste a live API key into the URL or a plain query field on
  camera. We use a keyless API in the lab and point to n8n's credential
  types (header or query auth) for any key.
- They say activate; current n8n says publish, and the production URL
  only answers once published. We use the words on screen today.
- Nobody mentions that the test URL listens only for a short window, or
  that one path and method can hold only one webhook. We say both.
- Long biography and theory before the first click. We give one sentence
  of why, then build.

## What we take (structure only)

1. Name the two URLs, test and production, in the first minute.
2. Prove the call outside n8n first (a browser tab), then move it into a
   node and compare the answer.
3. Read the provider's docs on screen and copy parameter names from them,
   not from memory.
4. Turn one hard-coded value into a mapped one, so the viewer sees the
   webhook input flow into the request.
5. Close the loop: the answer returns to whoever called the webhook, and
   that reply is the check that it worked.
