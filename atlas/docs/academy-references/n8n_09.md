## How they open

n8n's advanced-course video names the idea at once: a node that lets one
workflow call another, then promises scalability and faster building.
Bradford Carlton opens with a confession that he struggled for months to make
branches run side by side, and shows the slow version first. Valerian Valkin
opens on a question he saw on a forum and frames a sub-workflow as a function
with inputs and outputs. Only the n8n video explains the basic idea; the other
two are about one specific trick each.

## The order they explain things

- n8n: what a sub-workflow is, why (the same lookup needed in many
  places, one fix updates every caller), two warnings (keep field names
  identical on both sides, and the last node's items are what comes back),
  then a demo that cuts a lookup out of a workflow, pastes it into a new one
  started by the call trigger, and fetches its ID from the address bar.
- Bradford Carlton: the slow one-at-a-time run first, then the same steps in
  a child, called once per item with waiting switched off, then a comparison
  of run times and a pointer to the executions list.
- Valerian Valkin: the function analogy, the trigger's input types having no
  file option, the two workarounds (accept all data, or encode the file as
  text and rebuild it in the child), then a test through the executions list.

## Examples and analogies

- A sub-workflow as a function: it takes inputs and gives back outputs
  (Valerian Valkin).
- A lookup used in many workflows, fixed once (n8n).
- Seven apple names each given a sentence, timed in sequence and in parallel,
  about a third of the time (Bradford Carlton).
- A receipt image turned into text and back into a file across the call
  (Valerian Valkin).

## Beginner mistakes they address

- A capital letter in one workflow and a small one in the other, so the child
  cannot find the field (n8n).
- Not knowing which node is last, so the wrong data comes back (n8n).
- Messy nested input; flatten fields to the top level before the call (n8n).
- Expecting parallel runs while the parent still waits for each child
  (Bradford).
- Trying to pass a file straight through; the trigger has no file type, so
  encode it first or accept all data (Valerian).
- Testing a child alone with no input; use the executions list instead
  (Valerian).

## What they do badly, and what we do better

- None teaches the shortcut that turns nodes you already built into a child;
  we do, with its rules.
- None shows the three input modes of the call trigger side by side.
- Bradford's trick is real but advanced and he states it as a discovery
  without saying what could go wrong when the parent stops waiting. We leave
  parallel runs as a single sentence about the wait setting.
- Valerian's video drifts to a file-handling topic and a third-party OCR
  step. We do not teach it; we mention nothing about files.
- Two of the three are shown inside a messy real workflow; ours is a tiny
  lab with two nodes.

## What we take (structure only)

1. Start from the pain, the same steps copied between workflows.
2. Child first (trigger, steps), then parent (call), then what comes back.
3. Say that the last node's output is the answer.
4. Say to keep field names identical on both sides, capital letters included.
5. The wait setting as the one switch that changes the parent's behaviour.
6. Then the shortcut, so the viewer need not rebuild what exists.
