## How they open

Each names a concrete outcome in its first sentences. codebasics frames a business story (an HR assistant answering leave questions for a named colleague) and draws the architecture before any code. Postman promises a first server in under five minutes and then spends the first two on a concept segment. Zen van Riel shows an existing book API answering plain requests first, then promises that an AI will create books through it by the end.

## The order they explain things

- codebasics: the use case and a database-client-server diagram, installing the desktop client, the Python SDK and uv, a new project, the server code (generated with a chatbot, then edited), installing it into the client, testing questions about leave balances.
- Postman: why hard-coded API calls were limiting, tools versus resources versus prompts, the three parts of a server file, prerequisites, a TypeScript weather server pasted in, the config that connects it to Claude, a live weather question.
- Zen van Riel: the plain REST API working with curl, why an AI cannot call it directly, wrapping the FastAPI app with a converter library, the API still working as before, connecting the server to an editor's agent, the agent creating a book.

## Examples and analogies

- A leave-management helper over a mock table of two employees (codebasics).

- A mechanic micromanaged wrench by wrench, against one handed a full toolbox and trusted to choose (Postman).

## Beginner mistakes they address

- Thinking an AI can call an ordinary REST endpoint by itself (Zen van Riel).
- Missing prerequisites: the desktop client, the SDK, the package manager (codebasics, Postman).
- Not restarting the client after editing its config (codebasics).
- Writing to standard output in a local server, which breaks the protocol (implied in Postman's logging aside; our own docs say it outright).

## Pacing

Measured: 8 to 14 minutes. Postman moves fastest once code starts but pastes most of it; codebasics talks through every install at a relaxed pace; Zen van Riel stays in the terminal and editor throughout. Chapters in all three name the stage (setup, code, connect, test), which is searchable.

## What they do badly, and what we do better

- Code pasted or generated by a chatbot and not read line by line; we read the server line by line (our chapter does).
- Mock data with no word about where real data would come from; we say what changes for real data and what must stay private.
- No check that fails first: tests only show success. We show a broken path and the fix.
- A converter that exposes every endpoint at once (Zen van Riel); we expose one tool on purpose.

## What we take (structure only)

1. One real, small use case named first (our opening-hours tool).
2. Setup in a single short chapter, then the server file read top to bottom.
3. Run it and check it with the inspector before any client.
4. Then call it from the workflow tool, and say where it runs.
5. End on the result working in the client.
